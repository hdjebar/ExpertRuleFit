## 1. Default `confirmatory_penalty=1e-8` can collapse the model (cause confirmed; fixed in 0.7.0)

Adding a single confirmatory rule can wipe out every generated rule.

| Setting (standardised synthetic credit data, n = 500, `max_rules=20`, `n_bootstrap=3`) | Stable features | Active | Train AUC |
|---|---|---|---|
| no confirmatory rule | 21 | 18 | 0.951 |
| 1 confirmatory rule, w_c = 1e-8 (old default) | 15 | 15 | **0.673** |
| 1 confirmatory rule, w_c = 1e-4 | 26 | 26 | 0.956 |
| 1 confirmatory rule, w_c = 1e-2 | 23 | 23 | 0.957 |

In a second synthetic case (the absorption fixture in `tests/test_confirmatory_diagnostics.py`, w_c = 1e-4), 13 features passed the bootstrap filter, but the final model kept only the two confirmatory rules non-zero. One of them, a pure 0/1 alternating "noise" rule, got a coefficient of about −0.98.

**Unscaled inputs hit the same problem.** On the unstandardised test fixture (a lognormal column ≈ 10³–10⁵), ExpertRuleFit gave train AUC ≈ 0.54 even with no confirmatory rule.

### 1a. Cause: saga stops early, without a warning, when one column is 10⁴ times larger

Scripts and raw results: `experiments/diagnostics/` (`diag_saga.py`, `diag_cv.py`, `diag_saga_std.py` and their `.json`). The design matrix is the collapsing case above: 6 linear terms + 19 RuleFit rules + 1 confirmatory rule (`country_risk > 2.5`). Environment: scikit-learn 1.9.1 (not the pinned stack; these are solver diagnostics, not results for the paper).

**Fixed C (= 1, l1_ratio = 0.5), so CV plays no part.** Each fit is run twice: library settings (tol 1e-4, max_iter 10,000) and a reference run (tol 1e-12, up to 2,000,000 iterations). The objective is C·NLL + elastic-net penalty in the solver's parametrisation.

| Column rescaling | max ‖row‖² (step ∝ 1/this) | saga iterations | ConvergenceWarning | Objective above reference | Confirmatory coef: saga / reference |
|---|---|---|---|---|---|
| w_c = 1e-8 | 1.0 × 10⁸ | 9,465 | **none** | **156.0** | **−1.06 / +0.23** |
| w_c = 1e-4 | 1.0 × 10⁴ | 2,548 | none | 0.71 | −0.02 / −0.10 |
| none (w = 1) | 71 | 282 | none | 0.0002 | 0 / 0 |

With w_c = 1e-8 the reference run itself did not converge in 2,000,000 iterations (one ConvergenceWarning). The library-setting fit stopped silently at an objective 156 units worse, with the confirmatory coefficient of the wrong sign.

**CV, as in the pipeline's final step** (`LogisticRegressionCV`, saga, 5 folds × 10 Cs × 6 l1 ratios):

| Column rescaling | Chosen C | saga iterations per fit: min / median / max | ConvergenceWarnings | Confirmatory coef |
|---|---|---|---|---|
| w_c = 1e-8 | 0.046 | **2 / 17** / 9,827 | **0** | −1.06 |
| w_c = 1e-4 | 2.78 | 1 / 169 / 2,974 | 0 | +0.13 |
| none | 0.36 | 1 / 108 / 1,826 | 0 | 0 |

**Conclusion.** The hypothesis holds. saga's step size is about 1/max‖row‖². With one column multiplied by 1/√w_c = 10⁴, the step is about 10⁶ times smaller than without rescaling, so the other coefficients barely move. saga's stopping rule (relative coefficient change < tol) is then met after a handful of iterations. scikit-learn raises no ConvergenceWarning because the criterion *was* met. The solution is far from the optimum (here with the wrong sign on the confirmatory coefficient), and since the CV and the bootstrap filter both rely on these fits, generated rules drop out.

### 1b. Fix in 0.7.0: internal standardisation + smaller weight ratio (default w_c = 1e-2, see §8)

- `standardize=True` (new, default): candidate columns are standardised with training statistics (linear terms centred and scaled; rule and expert columns scaled only, to stay sparse), stored for prediction and covered by `save`/`load`. Coefficients and the intercept are reported on the original scale. Models saved before 0.7 load as unstandardised.
- `confirmatory_penalty` default 1e-8 → 1e-4, then → **1e-2** before release (§8). 0.7.0 ships with 1e-2.

Observations:

1. **Solver health.** In the pinned stack (unlike scikit-learn 1.9 in §1a), saga does raise ConvergenceWarnings, and their number falls monotonically with w_c: hundreds per fit at 1e-8, a few at the 1e-4 default, none from 1e-2. Fit time falls by 3× from 1e-4 to 1e-2.
2. **Accuracy.** w_c = 1e-8 still degrades the model even with standardisation (AUC −0.03 to −0.04, Brier 0.229 vs about 0.16). From 1e-6 upwards, AUC varies within 0.784–0.797 on one split, which is within the run-to-run spread to expect from a single 200-row test set. No w_c ≥ 1e-6 is clearly better on discrimination.
3. **Sign flip is real, not a solver artefact.** In the fits without convergence warnings (w_c ≥ 1e-2), the coefficient of "checking account < 0 DM" is negative, while the rule is marginally risk-increasing (49 % bad vs 30 % overall). The model also keeps `linear:Attribute1` (the ordinal checking-status code, max |corr| 0.77 with the rule) and several generated rules with the clause `Attribute1 <= 0.5`, which is the same condition. Those terms carry the effect, and the conditional coefficient of the expert rule turns negative. The A2 sign check flags it (`confirmatory_sign_ok_ = False`) and the diagnostics name `linear:Attribute1` as the most correlated term. The positive signs at 1e-8 and 1e-6 come from fits with 66–361 ConvergenceWarnings and should not be read as "the expert's sign holds".
4. **Rule-set sensitivity.** Jaccard against the default rule set is 0.92–1.00 for w_c ∈ {1e-6, 1e-4} and 0.75–0.79 for w_c ∈ {1e-2, 1}; w_o matters less than w_c.
5. **Optional rule** ("duration > 24 months") was kept in every fit.

**Recommendation:** w_c in [1e-2, 1]; adopted as the 0.7.0 default (1e-2), see §8. In this run, that is the range with no ConvergenceWarnings, AUC within the default's range or better, and fits 3–6× faster. Below 1e-2 the solver is not reliable, and the confirmatory coefficient there is not interpretable. The German result also strengthens the case for C3: what an expert needs from a confirmatory rule is a sign-constrained, unpenalised block, not a near-zero weight.

## 8. Decision: default w_c = 1e-2 in 0.7.0 (23/11/2026)

`confirmatory_penalty` defaults to **1e-2** in 0.7.0; there is no intermediate release with 1e-4.

- **Why 1e-2.** After standardisation, solver conditioning depends on the ratio 1/√w_c between a confirmatory column and the others, not on the dataset. 1e-2 (a factor 10) is the smallest weight in the B3 grid that fitted without ConvergenceWarnings on German Credit, at equal or better test AUC than 1e-4 and 3× faster. HMEQ and Taiwan B3 runs are confirmation, not a blocker.
- **The expected sign at 1e-8 came from non-convergence.** In B3, the confirmatory rule "checking account < 0 DM" had the expected positive coefficient only at w_c = 1e-8 (+0.06 to +0.07; 360–361 ConvergenceWarnings per fit) and 1e-6 (+0.25 to +0.27; 66–69 warnings). Those signs are artefacts of fits that had not converged. In every converged fit (w_c ≥ 1e-2), the conditional coefficient was negative. Results produced with the old default must not be cited as evidence that the expert's direction holds.
- **What 1e-2 does not fix.** It makes the fits reliable. It does not make the confirmatory coefficient follow the expert's sign. That is C3, now the first item of Phase C (`ACTION_PLAN.md`).
- **Inclusion** of confirmatory rules is unchanged: they bypass the frequency filter, and the post-hoc refit restores any the solver zeroes.

## 10. A5: leakage (23/11/2026)

- `DualModel` stacking was already clean: each fold's EBM and ExpertRuleFit are fitted on the training fold and predict only the held-out fold (`tests/test_leakage.py`, with a mutation check: making a fold EBM train on all rows fails the test).

## 15. D3: candidate rules are imodels' own Lasso selection (23/11/2026)

Read in the pinned image (imodels 3.0.4): `RuleFitClassifier.fit` → `_extract_rules` (fixed-seed boosting, all rules) → `_score_rules` → `score_linear(..., max_rules=50)`, which picks the L1 penalty of a `liblinear` logistic path leaving at most 50 non-zero rules and **returns only those rules** (`rules_without_feature_names_`). So:
- ExpertRuleFit's candidate rules (before 0.8.0, and still by default) are RuleFit's own L1 selection at seed 42, made **before** expert rules are added and before our filter runs; the filter only re-selects among them.
- This explains the B2 result that fixed-seed RuleFit matches ExpertRuleFit: both start from the same Lasso-selected rules.
- **Fix (option, not default):** `candidates="trees"` (`TreeRuleCandidates`) takes every distinct rule of the same fixed-seed ensemble (support in [0.01, 0.99], identical activation vectors merged, lexicographic order), so selection happens only in ExpertRuleFit, with expert rules present. It is slower, because there are many more candidates. Making it the default is a method change, left to the author after B1.

## 16. D4 and the 0.8.0 defaults (23/11/2026)

- **D4:** the n-out-of-n bootstrap with replacement put duplicated rows into both the training and validation folds of the inner 3-fold CV. The default is now `resampling="subsample"`: complementary pairs of stratified half-samples without replacement (the CPSS sampling scheme of Shah & Samworth 2013, without its error bound), 10 draws = 5 pairs, seeds `_BASE_SEED + k`. Side effects: about half the cost per draw, and a stricter filter at τ = 0.8, since half-samples select fewer columns. German kept 27 terms instead of 43 (Table 1 rerun).
- **Decisions 1–4 implemented:** `row_order="canonical"` and `confirmatory_mode="constrained"` are the defaults; sign bounds apply only to rules that declare `expected_sign`, and other confirmatory rules are unpenalised and free; `strict=True` raises `ConfirmatoryBoundError`; the audit bundle lists `confirmatory_bound_active`. Version 0.8.0. Models saved by older versions load with the settings they were fitted with (`as_given`, `refit`, `bootstrap`, `rulefit`).
- **Consequence for users:** expert rules must be row-wise functions of X. A rule built from row position is reordered by the canonical sort; one test used such a rule and was fixed.
- `calibration` is not supported with `confirmatory_mode="constrained"`; use `confirmatory_mode="refit"` if calibration is needed.

## 17. B1: stability under data perturbation, German Credit (23/11/2026, pinned stack)

| RuleFit, fixed seed | 0.014 (0.006) | 0.028 | **0.530** (0.035) | **0.056** | **0.210** | **0.095** | **0.785** (0.011) | 43.8 + 1.8 | 3 s |

Metrics are over the 300 pairs of perturbed fits. "Semantic" is the Hungarian-matched Jaccard of rule activation sets on the test rows, which forgives threshold jitter. Prediction SD is the mean per-row SD of test probabilities. Ambiguity is the share of test rows whose predicted class differs between at least two fits; discrepancy is the largest share on which one fit disagrees with the full-data fit (Marx et al. 2020).

**Reading.**
- The frequency filter makes ExpertRuleFit **less** stable on every measure (semantic 0.414 vs 0.527, prediction SD 0.087 vs 0.079, ambiguity 0.395 vs 0.375), costs 0.010 AUC and takes about 8× the runtime. Following the decision rule set on 23/11, **`selection="none"` is now the default** (still 0.8.0) and the filter stays available as `selection="bootstrap"`.
- Fixed-seed RuleFit is as stable as ExpertRuleFit without the filter on rule semantics (0.530 vs 0.527) and **more** stable on predictions (SD 0.056 vs 0.079, ambiguity 0.210 vs 0.375), at the same AUC. So on this dataset ExpertRuleFit offers no stability advantage over fixed-seed RuleFit. Its remaining contributions are determinism with canonical row order, the constrained confirmatory block, and the diagnostics and fingerprints.
- Exact Jaccard is near zero for every arm (0.003–0.025), while semantic similarity is 0.41–0.53: most "different" rules differ only in their thresholds.
- **Column order also matters.** The full-training-split ERF fit in B1 (AUC 0.770, filter on) differs from the same configuration in the filter-on Table 1 rerun (0.794). The two scripts' preprocessors order the columns differently (numeric first, versus original order), which changes rule names, the canonical row sort and the tree ensemble. Canonicalising column order is review 4's A8 and is still open.
- **Limits:** one dataset, one split, 25 subsamples, no expert rules. HMEQ and Taiwan are pending (`python experiments/b1_stability.py --dataset hmeq`).
